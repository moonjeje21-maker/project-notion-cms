# Living Wishlist MVP PRD

작성일: 2026-10-09 · 기준 문서: `plans/2026-10-09-project-notion-cms-interior-service-plan.md` (초안 v4), `plans/2026-10-09-project-notion-cms-prd-living-wishlist-fix-plan.md` (검증 보정)
갱신일: 2026-10-11 (Task 002까지의 구현 반영. 진행 상태는 `docs/roadmap/ROADMAP.md`)

## 📌 가정

- **종류 칩 목록 생성 방식**: Notion에서 종류를 추가하면 코드 수정 없이 웹 필터에 나타나야 하므로, 칩은 "가져온 소품들의 종류 값을 중복 제거"하여 만든다고 가정한다. 따라서 소품이 하나도 없는 종류는 칩에 나오지 않는다. 종류가 비어 있는 소품은 "기타" 칩으로 묶이며, 그런 소품이 하나라도 있으면 "기타" 칩은 맨 끝에 둔다
- **칩 순서**: "전체"가 맨 앞, 그 뒤는 소품 목록에 처음 등장한 순서(최근 추가 역순 기준)로 가정한다
- **카드 이미지 크기**: 이미지는 정사각형 영역에 맞춰 잘라 보여 준다(`object-cover`). 비었거나 깨졌을 때의 대체 그림도 같은 크기로 그린다
- **링크 없는 카드 모양**: 상품 링크가 빈 카드는 눌리지 않는 모양(기본 커서, 흐린 배지)으로 구분해, 눌러도 아무 일이 없는 이유를 알 수 있게 한다
- **`@notionhq/client` 버전**: 2026-10-11 Task 002에서 5.27.0 설치 완료. 전체 행 수집은 `collectPaginatedAPI`로 한다 (SDK의 `collectAllDataSourceRows`는 정렬을 `created_time` 오름차순으로 고정해 쓰지 않음)
- **머리글의 기존 요소(다크 모드 전환 버튼 등)**: 스타터 킷 틀에 이미 들어 있는 부품이므로 이 PRD의 기능 명세에는 넣지 않고 그대로 둔다
- **Notion 연결 실패 화면**: 저장소에 이미 있는 공용 오류 화면("다시 시도" 버튼)을 그대로 쓰며, 별도 페이지로 만들지 않는다. 소품 목록 페이지의 오류 상태로 취급한다
- **배포**: 기획 문서상 배포는 다음 단계지만, 기술 스택 섹션에는 예정 플랫폼(Vercel)을 함께 적는다

## 🎯 핵심 정보

**목적**: 사고 싶은 인테리어 소품(가구·조명·화분·수납 등)을 Notion 표에 "이름 + 상품 링크"만 적으면 웹 한 화면에 카드로 모여 보여서, 흩어진 후보를 한곳에서 훑어보고 구매를 결정할 수 있게 한다.
**사용자**: 본인(Notion에서 입력)과 주소를 공유받은 지인 몇 명(웹에서 읽기 전용). 로그인 없음. 검색 엔진 색인은 막지 않는다 (2026-10-09 결정).
**사이트 이름**: Living Wishlist (기획 문서 10장, 2026-10-09 결정. Notion 데이터베이스 이름도 같다. 고유명사라 영어 그대로 쓰고, 그 외 화면 문구는 프로젝트 규칙대로 한국어). 값은 `lib/site.ts` 한 곳에만 둔다.

## 🚶 사용자 여정

```
1. 소품 목록 페이지 (홈, 주소 접속 시 바로 표시)
   ↓ 서버가 Notion에서 소품 전체를 읽어 카드 그리드로 그림 (최근 추가가 위)

   [Notion 연결 실패] → 오류 상태 표시 ("다시 시도" 버튼) → 버튼 클릭 → 1번으로 다시 불러오기
   [소품 0개]        → 빈 상태 문구 "아직 소품이 없어요" 표시 (종류 칩도 보이지 않음) → 종료
   [소품 1개 이상]   → 종류 칩("전체" + 종류들) + 카드 그리드 표시
   ↓

2. 종류 칩 선택 (선택 사항, 브라우저 안에서만 동작·주소 변화 없음)
   ↓ 칩 클릭

   [해당 종류 소품 있음] → 카드 그리드가 그 종류만으로 바뀜
   [해당 종류 소품 없음] → 빈 상태 문구 "이 종류의 소품이 없어요" 표시
   ["전체" 칩 클릭]      → 모든 카드로 복귀
   ↓

3. 카드 클릭
   ↓

   [상품 링크 있음] → 쇼핑몰 상품 페이지가 새 탭으로 열림 (현재 탭은 목록 유지)
   [상품 링크 없음] → 아무 일도 일어나지 않음 (카드는 보이기만 함)
   ↓

4. 완료 → 목록으로 돌아와 다른 카드 보기 / 다른 종류 칩 선택
   (Notion에서 고친 내용은 약 5분 뒤 방문 시 자동 반영. 개발 서버에서는 즉시 반영)
```

- 자동 리디렉션은 없다. 페이지 밖으로 나가는 이동은 카드를 눌러 새 탭을 여는 것뿐이다

## ⚡ 기능 명세

### 1. MVP 핵심 기능

| ID | 기능명 | 설명 | MVP 필수 이유 | 관련 페이지 |
|----|--------|------|-------------|------------|
| **[F001]** | 소품 목록 카드 그리드 | Notion 데이터베이스의 소품 전체(이름·상품 링크·종류·이미지 URL)를 가져와 카드(이미지·이름·종류 배지)로 보여준다. 순서는 Notion 생성 시각 역순(최근 추가가 위). 반응형: 휴대폰 2열, 데스크톱 4열 | 서비스의 존재 이유인 "모아보기" 그 자체 | 소품 목록 페이지 |
| **[F002]** | 구매 링크 새 탭 열기 | 카드를 누르면 Notion의 "상품 링크"가 새 탭으로 열린다 (`target="_blank"`에 `rel="noopener noreferrer"`를 함께 둬 새 탭이 원래 탭을 조작하지 못하게 한다). 링크가 비어 있으면 눌러도 이동하지 않는다 | 모아본 뒤 바로 구매 페이지로 가야 "구매 결정"이 이어짐 | 소품 목록 페이지 |
| **[F003]** | 종류 칩 필터 | 상단에 "전체" + 종류 칩을 나열하고, 누르면 그 종류의 카드만 보인다. 브라우저 안에서만 동작하며 주소는 바뀌지 않는다 (주소 쿼리로 서버에서 거르면 매번 새로 그리는 동적 페이지가 되어 F010의 캐시가 무력화되기 때문). 칩 목록은 소품들의 종류 값에서 자동으로 만들어져 Notion에 종류를 추가해도 코드 수정이 없다 | 소품이 쌓이면 종류별로 훑어보지 않으면 비교가 안 됨 | 소품 목록 페이지 |
| **[F004]** | 빈 상태·대체 이미지 표시 | 소품 0개 → "아직 소품이 없어요", 필터 결과 0개 → "이 종류의 소품이 없어요". 이미지 URL이 비었거나 깨지면 회색 배경 + 아이콘 대체 그림. 종류가 비어 있으면 "기타" 배지 | Notion 필수 입력이 2칸뿐이라 빈 값이 흔함. 빈 값에도 화면이 깨지지 않아야 "이름+링크만 넣는" 입력 원칙이 유지됨 | 소품 목록 페이지 |

### 2. MVP 필수 지원 기능

| ID | 기능명 | 설명 | MVP 필수 이유 | 관련 페이지 |
|----|--------|------|-------------|------------|
| **[F010]** | Notion 자동 갱신 | 페이지를 미리 만들어 두고 약 5분이 지나면 다음 방문 때 뒤에서 Notion을 다시 읽어 새로 만든다(ISR). 방문자는 항상 빠르고, Notion에서 고친 내용은 몇 분 안에 반영된다. 구현: `cacheComponents`는 켜지 않고, 소품 목록 페이지 파일에 `export const revalidate = 300`을 둔다. 개발 서버(`npm run dev`)에서는 캐시가 동작하지 않으므로 "5분 뒤 반영" 확인은 `npm run build && npm run start`로 한다 | Notion을 CMS로 쓰는 이유 자체. 수동 재배포 없이 "Notion에 한 줄 추가 → 웹 반영"이 돼야 함 | 소품 목록 페이지 |
| **[F011]** | Notion 연결 오류 표시 | Notion 읽기에 실패하면(API 키·데이터 소스 ID 오류, 네트워크 끊김 등) 공용 오류 화면("다시 시도" 버튼)을 보여주고, 버튼을 누르면 `retry` prop으로 다시 불러온다. 배포본에서는 재생성이 실패해도 이전 내용이 유지되므로, 오류 화면은 캐시가 없는 첫 렌더나 개발 환경에서 주로 보인다. 배포 전에 Vercel 환경변수(`NOTION_API_KEY`, `NOTION_DATA_SOURCE_ID`)를 먼저 등록한다 | 외부 서비스 의존 기능이라 실패 시 빈 화면이 아닌 복구 수단이 필요 | 소품 목록 페이지 |

### 3. MVP 이후 1차: 입력 도우미 (2026-10-26 추가)

MVP를 다 쓴 뒤 "이름 + 상품 링크"만 적는 입력 원칙을 지키면서 그림을 채우기 위해 추가한 기능. 번호는 핵심 00x·지원 01x 다음 묶음인 02x를 쓴다 (F012는 2026-10-09 결정대로 비워 둔다).

| ID | 기능명 | 설명 | 필요한 이유 | 관련 페이지 |
|----|--------|------|-------------|------------|
| **[F020]** | 이미지 URL 자동 채우기 (로컬 스크립트) | 사용자가 내 컴퓨터에서 `npm run fill-images`를 실행하면, "이미지 URL"이 비었거나 그림이 아닌 행의 "상품 링크"를 열어 대표 이미지를 찾아 Notion의 "이미지 URL" 열에 써 넣는다. 찾는 순서: Shopify 공개 상품 JSON(`/products/<handle>.json`) → 페이지의 `og:image` → `twitter:image`. 찾은 주소는 `http(s)://` 검사와 `content-type: image/*` 확인을 통과해야 저장한다. 기본은 미리보기(쓰지 않음)이고 `--write`를 붙여야 실제로 쓴다. 요청은 우리 서비스 이름을 밝힌 User-Agent로만 보내고 브라우저로 위장하지 않는다. 사이트가 거부(429 등)하면 `못 찾음`으로 두고 사람이 Notion에 직접 적는다. 사이트(`src/`)는 계속 Notion을 읽기만 하며, Notion에 쓰는 코드는 이 스크립트뿐이다 (통합 권한 "콘텐츠 업데이트" 필요, "콘텐츠 삽입"은 끔) | 2026-10-26 실측에서 10개 링크 중 4개(imweb·WooCommerce·Shopify)는 정직한 요청으로 그림을 얻을 수 있었다. 사람이 "이미지 주소 복사"를 반복하는 수고를 줄이되, 사이트 런타임에서 매번 외부 페이지를 열면 Vercel 데이터센터 IP가 차단되고 실패가 조용히 묻히므로 로컬 1회성 스크립트로 한다 | 없음 (터미널 명령. 결과는 약 5분 뒤 소품 목록 페이지에 반영, F010) |

### 4. MVP 이후 기능 (제외)

- 소품 상세 페이지 (현재는 카드와 보여줄 정보가 같음. 가격·크기가 생기면 그때 만든다)
- 가격·크기 표시와 비교, 상품 링크에서 가격 자동 수집 (이미지 자동 채우기는 2026-10-26 F020으로 이동)
- 네이버 상품 이미지 채우기 (네이버는 봇 요청을 429로 거부. 정직한 길은 네이버 검색 Open API인데 개발자 키가 필요해 2026-10-26 사용자 결정으로 보류)
- 사이트 런타임(ISR)에서의 이미지 자동 수집 (Vercel 데이터센터 IP 차단 위험. 로컬 스크립트가 안정된 뒤 검토)
- 정렬 선택 (최신순 외 가격순 등)
- 필터 값을 주소에 담아 공유 (주소 쿼리 필터)
- 공간별(거실·침실 등) 필터, 이름 검색
- 비교 화면 (여러 소품 나란히 보기)
- 로그인, 웹에서 직접 입력 (입력은 Notion에서만)
- Notion Web Clipper로 저장 시 이 데이터베이스로 들어가게 하는 설정 (입력 편의, 확인만 필요)

```
└── 🏠 홈 (소품 목록 페이지)

    ├── 기능: F002 (구매 링크 새 탭 열기)

    └── 기능: F011 (Notion 연결 오류 표시)
```

- 메뉴 항목은 "홈" 하나다. 머리글 왼쪽에는 사이트 이름 "Living Wishlist"(로고 자리), 오른쪽에는 스타터 킷의 다크 모드 전환 버튼만 남긴다. 사이트 이름을 눌러도 홈으로 간다

- 스타터 킷의 대시보드 틀(사이드바 + 상단 바)은 쓰지 않는다. `lib/site.ts`의 `mainNav`를 "홈" 하나로 줄이고, `(dashboard)` 경로는 삭제한다 (색인을 막지 않으므로 남겨 두면 스타터 킷 화면이 검색에 노출될 수 있다. 반드시 삭제한다)

## 📄 페이지별 상세 기능

### 소품 목록 페이지 (홈)

> **구현 기능:** `F001`, `F002`, `F003`, `F004`, `F010`, `F011` | **메뉴 위치:** 머리글 "홈" / 사이트 이름 클릭 | **인증:** 없음

| 항목 | 내용 |
|------|------|
| **역할** | 서비스의 유일한 화면. Notion에 모아 둔 인테리어 소품 후보를 카드 그리드로 한눈에 보여주는 랜딩 겸 핵심 작업 페이지 |

## 🗄️ 데이터 모델

데이터 저장소는 **Notion 데이터베이스**다. 웹 쪽에는 별도 데이터베이스가 없고, Notion 응답을 화면용 객체로 바꿔서만 쓴다.

### Living Wishlist (Notion 데이터베이스, 2026-10-09 생성 완료, 입력은 Notion에서만)

열 이름은 코드에서 그대로 참조하므로 한 번 정하면 바꾸지 않는다. 매번 채우는 칸은 **이름 · 상품 링크** 2개다.

| 속성(열) | 설명 | 관계 |
|------|------|------|
| 이름 | 소품 이름. Notion 제목 속성, **필수** (비울 수 없음) | |
| 상품 링크 | 쇼핑몰 상품 페이지 주소. **필수** 입력. 비어 있으면 카드를 눌러도 이동하지 않음 | |
| 종류 | 선택(Select) 속성. 시작 선택지: 가구·조명·화분·수납·러그·소품. 비어 있으면 웹에서 "기타"로 표시. Notion에서 선택지를 추가하면 웹 필터에도 자동 반영 | → 소품 목록 페이지의 종류 칩 |
| 이미지 URL | 쇼핑몰 사진의 "이미지 주소 복사"로 얻은 외부 주소. 선택 입력. 비어 있거나 깨지면 대체 그림. Notion에 직접 올린 사진은 주소가 1시간마다 바뀌어 쓰지 않음. 비워 두면 로컬에서 `npm run fill-images -- --write`로 채울 수 있다 (F020, 지원되는 사이트만) | ← F020 스크립트가 쓰는 유일한 열 |
| (생성 시각) | Notion이 자동으로 기록. 목록 정렬 기준(역순) | |

- 2026-10-11 실제 확인(Task 002): 열 타입은 `이름`=제목(title), `상품 링크`=URL, `종류`=선택(select), `이미지 URL`=URL. 7행
- 웹에서 빼고 싶은 소품은 Notion에서 행을 지우거나 보관(archive)한다. "공개" 체크박스 열은 두지 않는다
- **조회 키**: Notion 앱 "데이터 소스 관리 → 데이터 소스 ID 복사"로 얻은 **데이터 소스 ID**를 쓴다 (환경변수 `NOTION_DATA_SOURCE_ID`. API 키는 `NOTION_API_KEY`. 둘 다 `.env.local`에 두고 git에 올리지 않는다). 데이터베이스 ID와 호환되지 않으므로 섞어 쓰지 않는다. 소품이 100개를 넘어도 전부 가져오도록 `collectPaginatedAPI`로 `next_cursor`를 끝까지 따라가며 조회한다. 구현은 `src/lib/notion.ts`의 `fetchAllRows()`(Task 002), `Item` 매핑은 Task 006

### Item (화면용 변환 객체, 저장하지 않음)

Notion 응답을 화면이 쓰기 쉬운 형태로 바꾼 객체. 열 이름 ↔ 필드 매핑은 Notion 연동 코드 한 파일에만 둔다. 구현: `src/lib/items.ts`의 `Item` 타입과 `OTHER_CATEGORY = "기타"` 상수 (Task 001)

| 필드 | 설명 | 관계 |
|------|------|------|
| id | Notion 페이지(행) 고유 식별자 | → Living Wishlist.(행) |
| name | 이름 | ← Living Wishlist.이름 |
| url | 상품 링크 (없으면 비어 있음) | ← Living Wishlist.상품 링크 |
| imageUrl | 이미지 URL (없으면 비어 있음) | ← Living Wishlist.이미지 URL |
| category | 종류 (없으면 "기타") | ← Living Wishlist.종류 |
